# Duplicate Work Detection

Recurring and multi-agent workflows accumulate near-duplicate PRs, issues, and branches when each run checks only "did I already finish this" instead of "does an equivalent open item already exist, from this run or any other." The failure is invisible to the run that creates the duplicate — it succeeds and reports normally — and only shows up later as pile-up that a maintainer has to untangle.

## Procedure

1. **Before creating anything with a name or identity (branch, PR, issue, file, scheduled export), list existing open candidates first.** For PRs/issues: query by state=open across all authors, not just ones you created. For branches/files: list by name pattern or recent-activity, not just your last known state.
2. **Match on intent, not just exact title.** A PR titled differently but touching the same files, closing the same gap, or solving the same recurring task is a duplicate candidate even if generated by a different run or a human. Read the diff/body, not only the title.
3. **Prefer updating the existing item over opening a new one.** If a matching open PR/issue/branch exists, push additional commits to it, edit its description, or comment with the new findings — don't open a second one that fragments the discussion and the diff history.
4. **If multiple stale candidates exist, consolidate rather than add a third.** Note which one is the correct target (most recent commits, clearest scope) and either close the losing duplicates with a pointer or merge their useful content into the one you keep — only after confirming you have authority to do so.
5. **When genuinely uncertain whether two items are the same work**, err toward reusing/updating and explaining the overlap in your report, rather than silently creating a parallel item "to be safe."
6. **Record the check in your output.** State explicitly what you searched (state, filters, time range) and what you found, so a reviewer can tell duplicate-avoidance was actually performed, not assumed.

## Guardrails and pitfalls

- Do not rely only on `git log --oneline` of your own branch history; branches and PRs opened by other runs, humans, or bots won't appear there — query the hosting platform (`gh pr list --state all`, `gh issue list --state all`) directly.
- Do not treat "no open PR with this exact title" as proof no duplicate exists — titles drift between runs even when the underlying task is identical.
- Do not force-reuse an unrelated open item just because it touches the same directory; a superficial overlap with a different purpose should stay separate.
- Do not silently close someone else's in-flight work as a "duplicate" without clear overlap evidence and without disclosing the action in your report.
- Watch for duplicate detection itself becoming stale: a candidate merged or closed seconds before your check can still look "open" in a cached listing — re-fetch rather than trusting an earlier snapshot in the same session.

## Verification

- [ ] An open-state search across all authors/sources was performed before creating a new identity-bearing artifact.
- [ ] Matches were evaluated by intent/diff content, not title string alone.
- [ ] An existing equivalent item was updated instead of duplicated, or the decision to create a new one is justified in the report.
- [ ] The report states what was searched and what was found, including "none found" explicitly rather than omitting the check.
